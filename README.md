# 翔仔居家公司工具

這是翔仔居家的純靜態公司工具入口。

- `/`：公司工具首頁。
- `/inventory/`：期初期末庫存資料整理。
- `/cost-analysis/`：A、B庫存成本稽核分析；在瀏覽器內整合八類 Excel 來源，比對 A 庫存推算耗用、B 淨銷售／跨體系成本與 C 非銷售調整。期初、期末可匯入全部店倉，分析後可切換「總部體系整體（沿用現行規則）」、「寬承總倉單倉」、「單一店倉」與「全部店倉總覽」；單倉模式依實體庫存計算直接進貨、調撥入／出、實際扣庫與非銷售出入庫，不等同門市完整損益。
- `/supplier-reconciliation/`：財務供應商對帳比對；在瀏覽器內按月比對 ERP 收貨單與供應商對帳報表，支援次月補收、前期認列扣抵及上林反向跨月追蹤，並輸出含兩種跨月台帳的九頁籤 Excel。跨月台帳會依供應商自動保存於目前瀏覽器的 IndexedDB、同月份重跑覆蓋且最多保留24個月；原始 Excel 不保存，換機仍可用結果 Excel 復原。
- `/procurement-planning/`：庫存採購規劃正式流程；原始 Excel 留在瀏覽器，固定 Google 來源唯讀取得，先產生母批次，再依每家實際供應商拆成獨立審核單位（普優瑪另拆天絲／天絲棉、長絨棉、無尺寸），各自完成回匯二次覆核、付款月份、核准摘要、集中額度台帳與 ERP 採購檔。一般採購、新品首批、人工匯入及補登已採購單在核准／補登時都保存ERP品號、品名、供應商、核准量、未稅單價及金額；舊版補登若只有總額，可重新匯入同ERP單號且同總額的原始採購檔安全補回逐品項基準，不重複占用額度。ERP匯入完成後，採購人員直接在「已承諾批次與額度異動」的該筆批次回填ERP單號；後續匯入完整狀態採購檔時，系統以ERP單號與品號核對原核准量、單價、收貨及未交量。正常收貨會自動更新，新增／刪除品項、數量或價格差異則另列「ERP差異待確認」，確認原因後更新原批次台帳，不重跑第一次與第二次回匯。若個別舊批次仍缺逐品項基準，系統會清楚提示並略過該單比對，不再中止整批採購建議。台帳每筆批次可展開查看原核准金額、ERP／調整後金額、承諾差額、ERP訂購量、累計實收與剩餘未到。門市週調撥核准後仍未配足的需求會在「採購方式與例外需求」集中回拋，頁首保留待辦提示；有待辦時預設展開，並可逐筆或批次併入下一張採購、另開補採新單、結案或取消。採購報表另列需求來源、最早需要日、未到貨最早到貨日、能否及時抵扣、時間缺口與本次新增量。只有已建立ERP且較新完整未到貨清單已不再出現的覆蓋量才轉為已到貨，後續週調撥部分／完整補配會累計並結案，人工結案或取消必須留下原因。SA／OA／SB／OB開頭品號及品名標示8×7尺的商品固定排除一般採購與寄庫；其中OA41361、OA42361、OA43361、OA44361以掛(S)組合品理由排除。產生第一步採購建議只建立本次成本試算，不會改動正式額度或公司共用成本快照；正式核准且通過本月銷售涵蓋與異常降幅檢查後，才會更新月份成本彙總與截止日。全程不會上傳原始Excel、檔名或逐列資料。
- `/store-transfer/`：門市週補貨與調撥；沿用主採購工具的公司Google OAuth、商品主檔、整體行銷策略及版本化門市庫存規則，庫存、銷售及期間調撥仍在瀏覽器本機運算。星期五／星期一遇公司不作業日會自動提前／順延；各店星期三／四到店設定可管理，建議量以實際開單日至下一輪預計到店日計算，並分開顯示本批到店、下一輪到店、到店後可售至與到貨前風險。展示缺口與可售需求分開相加；枕頭／枕芯會綜合商品主檔大類與軟枕、午安枕、頸枕等名稱辨識，R00、R06保留不可售展示2件；毛巾、浴巾、手巾及方巾可穩定辨識為無尺寸配件。一般非S品會依總部14／42／84天直接銷售保留安全庫存，S品仍依5件門檻與原周轉規則保護。B3只認列來源單號＋ERP品號配對成功且去重的總倉代出，例外會明列待人工確認。結果分為一般必要補貨、單人被套前2名花色建議備貨、活動／贈品、提袋耗材及獨立缺貨未配；活動贈品會依本批實際到店日截斷於活動結束日，並分辨全館或指定類別／系列／品項及其訂單門檻基礎，無法可靠辨識時不套用全館數據。第一階段建議預覽與第二階段批次詳細資料皆可切換「全部門市」或單一門市。缺貨未配會隨批次保存需求、已配、未配、原因與後續狀態，門市只看本店、總部看六店，且不進確認量或ERP。門市確認量與總部核准量會即時換算調撥後可售至，改量必填原因。門市與總部皆可人工新增品項；移除品項以該階段數量歸零處理，保留原始建議、原因與事件紀錄，ERP只輸出最後核准量大於0的品項。同一週重新建立批次時，新批次會成為目前作業版本，舊的等待門市／總部覆核批次自動標示為「已取代・僅供查閱」並停止修改與送出；總部可將已取代／已取消批次安全移出前台，但目前作業與已完成批次不能直接刪除，刪除者與完整稽核資料仍保留12個月。門市在鎖定前可撤回重填；總部可看六店狀態、逐店產生ERP並依`等待門市→總部覆核→已核准→ERP皆完成→本週完成`關閉批次。提袋累積至少4個可信週次後才以100個整箱建議。門市展示與最低庫存規則可依商品主檔的商品大類、尺寸屬性及品項關鍵字由管理前台直接新增；高優先序專屬規則先於通用規則套用。週調撥輸入沿用主採購工具的SheetJS 0.20.3讀取器，ERP輸出則保留樣式元件。近12週銷售建議按月拆分、每月一份，工具採逐份輕量讀取並預檢工作表實際展開大小。從週調撥工具進入規則管理時，麵包屑與返回按鈕會回到週調撥工具。
  - 6×7尺雙人薄被套若為天絲、華爾紗、純棉或精梳純棉，列可售最低庫存1件；其它材質維持不可售展示1件。材質會綜合品名與商品主檔大類判斷，避免品名未標示「精梳純棉」時漏判。
  - 正式補貨會把`提交`列為待發貨、`發貨審核`列為在途，與現有實體庫存分欄顯示；兩者只抵扣需求，不併入本次系統建議調撥量。若抵扣後建議量為0，品項不進主要建議或ERP檔，但仍保留在唯讀的既有調撥明細供核對。另提供A/B測試模式，完整排除`提交`單對門市與總倉的影響，且本機預覽不會直接建立正式批次或寫入提袋快照；計算完成後可依本次勾選門市，各自下載一份A/B調撥建議差異分析表，也可只發布計算結果為公司共用協作批次。協作批次不上傳原始Excel、檔名或來源逐列資料，以版本號防止多人相互覆蓋，定稿前門市不會看到。
  - 家飾配件會再依品名與主檔尺寸資訊分流：熊冷被、涼毯、蓋毯及M／L／XL等明確尺寸碼歸有尺寸配件；眼罩、束口袋、鞋袋、零錢包與香氛噴霧等歸無尺寸配件。拍照樣與展示專用品不套一般配件規則，4.5×6.5及8×7棉被也不會被重新納入展示。
  - 門市帳號在同一個週調撥網址會看到自己的操作入口，並可進入獨立的「本店展示例外」頁，以單一ERP貨號設定本店不可售展示最低量；門市例外優先於總部通用展示規則，總部只讀取套用，不與通用量相加。變更自下一次重算生效，已建立批次保留原規則快照，異動紀錄保留12個月。
  - 總部通用門市規則新增ERP品號精準欄，多個貨號可用逗號或「｜」分隔，儲存後依優先序由高至低排列。可售最低庫存仍要求近42天有該品號現場銷售；不可售展示不受42天零銷售影響。S品若總倉扣除提交占用及周轉保留後無可釋出量，該次重算取消展示需求，不產生展示缺貨未配或採購需求。

- 門市週調撥的棉被／被子展示規則：只有6×7尺列不可售展示1件，4.5×6.5尺與8×7尺不列展示；展示補足量不計入系統、門市確認或總部核准後的可售至日期。

## 庫存工具會做什麼

使用者可在頁面選擇 `.xlsx`，依品名分類為正常商品、排除項目與待人工確認，並下載包含四張工作表的新 Excel。

同事版操作手冊原始文件位於 `inventory/操作手冊.md`；前台已依公司工具 CIS 放在主要步驟之後、正式操作區之前，以「重點摘要＋可展開細節」呈現。

三張明細表會在「實際庫存成本額」後新增「實際庫存進貨額」。若來源表同時有「實際庫存」與「進貨價」，每列會用這兩欄相乘並在最後合計；工具會依欄名找到實際位置，因此新增欄位造成欄號位移時仍能引用正確欄位。若來源表缺少「進貨價」，新欄與合計列會明確標示未辨識，不會猜價格。

所有同事都會使用 Cloudflare D1 中的公司集中規則。`/inventory/` 與 `/cost-analysis/` 都會在「開啟頁面」及每次按「開始分析」前，透過同源的 `/api/rules` 再取最新版；若規則服務無法使用，會直接禁止分析，不會偷偷改用舊規則。`/supplier-reconciliation/` 不需呼叫規則 API，商品與金額只在瀏覽器內比對。

`/procurement-planning/` 依「營收與額度→最新資料→採購方式→建議與分批→回匯核准」五階段排列；第一區固定顯示關鍵金額，通路與計算欄位可展開。本月預估整月成本耗用依寬承預估認列營收及目前核准成本率自動計算；全部狀態採購單會分辨新單、主管審核、部分到貨、結案與全部到貨，並依收貨單開單日顯示本月至今實際收貨成本。銷售需求採「銷貨＋訂貨＋退貨＋退訂、取貨只用於辨識總倉代出」；SKU近期6／12週模型為主，類別模型只做季節需求池校正。季節模型正式版由Google Drive自動取得；每6個月到期時，前台才逐份讀取近三年歷史銷售、交易層級去重並建立草稿，由採購核准者發布正式版及寄送摘要，本機快取與手動選檔作備援。強夏季／強冬季品只有在SKU曲線可信度中／高且旺季高峰至少跨兩年重複時，才以同季歷史絕對量托住需求；一般天絲寢具改列四季夏偏旺、純棉寢具改列四季冬偏旺，只採40%季節變化並限制在0.8～1.3倍。採購需求分成總部與逐店需求，各店先扣自己的現有庫存，再從加總需求扣總部可用庫存及未到貨；通路營收預估會調整各通路需求。月初依熱銷70%、穩定50%、低銷0%分批釋放，月中與月底依最新缺口重算；寬沐營收45%只另列管理目標與差額，不自動灌入SKU建議。上林固定28天檢視並獨立分頁；力榮逐品號採0或10的倍數；凱信達、歐必斯、一次性代工與總部贈品排除一般自動採購。國外供應商只有在正常到貨／下次補貨範圍跨入年度停工區間時，才另加45～60天備貨（預設53天）；前台與Excel會分開顯示受影響SKU、額外數量及金額，而最後建議金額已包含該額外額度。計算完成後可逐家勾選供應商，預設主要名單為普優瑪寢具有限公司、力榮、上林、潤泰羽絨、泰能脊康；名單可在規則管理增減，未列入或臨時辨識到的廠商自動歸入其它。貨品狀態空白不再等同停產，工具會保留試算建議量並標示待人工確認；第一次回匯必須明確填量與原因。明確標示下架、停產或品名結尾`(S)`者仍維持硬性阻擋。前台即時重算所選範圍的採購金額、付款與額度，Excel只輸出所選供應商並保留稽核與核心規則頁；採購明細只保留03A～03D供應商頁籤，不再重複輸出02明細頁。採購報表只保留總部、門市系統需求與加總公式，不另設人工需求欄；「總倉目前庫存可售至」以總倉可用庫存與總部全通路日需求計算，作採購判斷，「全公司合計庫存可售至」則以總倉加所有門市可售庫存除以全通路日需求，只作整體管理參考；未到貨與本次採購另列於「全公司系統建議採購後可售至」與「全公司人工確認後可售至」。匯出Excel不啟用工作表密碼保護，所有欄位可直接編輯，但回匯時仍會重新檢查人工量、調整原因、採購單位與核准規則；第一次回匯有阻擋時只在前台列出錯誤，不產生覆核檔。第一次回匯通過後，工具下載單一「第一次覆核暨異動確認表」；原始建議量、第一次人工回匯量、第一次覆核量、第二次異動量與原因相鄰排列。若無異動可直接送待核准，不需再回匯；若有異動，只填變更列，留白沿用第一次覆核量，改量與填0取消都必須填原因。所有未完成母批次及分批審核會分列保存在目前瀏覽器並可個別續作，下載的採購建議報表另含隱藏續作資料，可供換機恢復；任一既有本機草稿可直接發布成公司共用協作草稿，授權同事可在不同電腦查看並接續回匯，更新採版本衝突保護。公司共用母批次固定置頂且不可移除；採購核准者可將不再使用的未完成子批次安全移出協作清單，不影響正式核准台帳、ERP或已下載檔案，並保留移除者與時間供12個月稽核。`04A_普優瑪寄庫建議`維持單一頁籤，依天絲／長絨棉／無尺寸、花色或同品項、床包／被套／枕套三級排列，並顯示中類及大類小計。供應商、主要顯示名單、國外春節停工備貨、寄庫、採購單位、門市庫存與黑名單集中在 `/procurement-planning/rules-admin/`，由採購核准者維護；一般備貨公式維持程式內建。中性情境同時顯示寬承認列營收與寬承＋寬沐終端通路預估，成本率只使用寬承認列營收；整月額度與目前已釋放額度分開顯示。固定 Google 來源按鈕會顯示載入中、四項來源各自結果及重新取得狀態；前台把自動來源與本次必要人工匯入分成兩組，五個自動來源卡片都可另開原始Google來源，普優瑪及力榮寄庫表皆為線上自動取得並可手動備援。舊版二次覆核檔仍會明確拒絕。只有正式核准後才寫入採購承諾、建立可重送的電子郵件通知並開放ERP檔案；ERP輸出固定為單一`通用貨品數量`頁籤及八欄原始匯入格式，不套採購報表CIS。完成ERP開單後只轉換互斥狀態，不重複占額。完整規格與尚待逐步擴充的門市展示、B3及耗材流程見 [`procurement-planning/NEXT_PHASE.md`](procurement-planning/NEXT_PHASE.md)。

`03A_力榮採購`與`04B_力榮寄庫建議`使用同一份力榮寄庫來源；採購頁同步顯示工廠現貨、已確認製作中、扣除兩者後的寄倉缺口，以及不超過工廠現貨的本次實際可拉回量。

固定 Google Drive／試算表的唯讀取得若遇到429或5xx暫時性服務異常，會短暫自動重試。重新取得仍失敗時，前台會明列「操作環節、失敗區塊、失敗階段、原因、處理結果與建議處理」，並保留本分頁先前成功取得的資料，不會把門市不足的批次處理誤寫成來源資料需要修正；只有個別來源持續失敗時才建議使用該來源的手動備援。

2026-09-18更新：採購與寄庫報表的三級分類統一改為「大類＝花色或同品項、中類＝品項、小類＝尺寸」；天絲／長絨棉／無尺寸只保留為材質分頁或區段。此規則套用普優瑪與力榮的採購及寄庫頁籤，取代前述將材質稱為大類的舊說明。

分批審核可複選多個供應商或普優瑪分類，合併成同一份人工審核報表與核准批次；下載按鈕設於分批選擇區。核准後的ERP採購檔仍依供應商分開產生，避免跨廠商混單。

公司共用母批次與各分批審核使用不同協作編號；從共用母批次開始力榮或其他子批次時，子批次不會沿用或覆蓋母批次。若偵測到舊版曾把子批次寫入母批次編號，使用本機母批次執行「更新協作草稿」時，會先把子批次另存保留，再恢復固定置頂的母批次。

每次下載分批審核報表後，前台會清空「下一批待勾選」狀態；已下載批次仍保留自己的續作與回匯資料，但不會自動帶入後續新批次。

普優瑪人工回匯若需把該品號目前全部寄庫現貨清回，可將人工調整原因精確填為「全部寄庫現貨清回」。工具會以寄庫現貨扣除正式未到貨及其他有效批次占用，人工量必須與剩餘可清回量完全相同才允許不受整箱倍數限制；粉紅排程不算當下現貨。第一次與第二次回匯都會重新檢核，舊報表原有的「最後剩餘數量」保留精確相容，但不接受模糊近似字詞。

同一春節週期較早建立、目前仍未到貨的正式採購量會先抵扣本次春節缺口，避免重跑時再次加量；採購報表以「前次春節備貨未交量」揭露抵扣依據。一般需求仍會依最新庫存、未到貨與季節曲線重新計算。

- `/inventory/`：一般工具頁，可查看及下載目前規則，不能修改。
- `/inventory/rules-admin/`：規則管理頁；以公司 Google 帳號登入，只允許指定管理者。
- 管理頁可新增、刪除、匯入及匯出 JSON；發布時有版本衝突保護。

來源 Excel 不會被改寫。期初期末庫存資料整理會把排除資料保留在「排除項目」，庫存成本分析則會在「04_來源檢查」列出各報表排除前後的列數、數量、來源金額與逐列排除原因，方便稽核。

## 資料安全

Cloudflare Worker 保存集中分類規則，以及採購流程必要的批次編號、供應商摘要、金額、互斥狀態、付款月份、核准事件與通知稽核；沒有 Excel 或檔案上傳 API，也不保存檔名。使用者主動按「發布協作草稿」後，才會保存計算後的逐品項採購建議、人工回匯結果與流程狀態，供公司授權帳號跨電腦接續；協作草稿及通知紀錄均於12個月後由每日排程清除。

Excel 的讀取、分類、統計與輸出全部在使用者目前的瀏覽器分頁或同源背景Worker完成，不會傳送到網站伺服器；只有季節模型草稿與正式輸出會另存到指定公司Google Drive資料夾。採購頁的 CSP 只額外允許 Google Identity、Drive、Sheets、Gmail、同源背景Worker與同源 API；OAuth access token 只留在分頁記憶體，不進 D1、localStorage 或伺服器日誌。採購工具另使用本機保存的 `xlsx-js-style` 產生帶有CIS底色、欄位提示與頁面間距的Excel，授權全文位於 `procurement-planning/assets/XLSX-JS-STYLE-LICENSE.txt`，不會從外部CDN載入。

「採購核准者」與「週調撥總部協作帳號」為兩份獨立權限名單，均由最高權限帳號在規則管理頁維護。週調撥總部協作帳號可查看全部門市、建立及核准調撥批次並產生ERP調撥檔，但不會因此取得採購核准權限；四位週調撥總部協作者都可查看與編輯A/B協作批次，僅`siang01@siangapato.com.tw`與`service1@siangapato.com.tw`可將協作定稿轉成正式批次。各門市帳號仍只能處理自己的門市資料。

請勿將真實庫存 Excel、測試輸出、客戶資料、密碼、API key 或環境設定提交到這個公開儲存庫。

## Cloudflare 部署與保護

Cloudflare 相關程式全部放在 `cloudflare/` 子目錄，避免 Zeabur 把網站根目錄誤判為 Node 專案；公司首頁與 `/inventory/` 仍是原本的純靜態站。

1. 建立 D1 `inventory-rules`，把實際 database ID 填入 `cloudflare/wrangler.jsonc`。
2. 執行 `wrangler d1 migrations apply inventory-rules --remote`，建立目前規則與歷史表。
3. 先部署到 `workers.dev` 測試 GET；此時 `ACCESS_TEAM_DOMAIN`、`ACCESS_AUD` 留空，管理 PUT 會 fail closed。
4. 在 Cloudflare Zero Trust 建立公司 Google Identity Provider。
5. 建立 Self-hosted Access application，保護 `siangstock.com/inventory/rules-admin/*` 與 `siangstock.com/api/rules/admin*`，規則採預設拒絕，只 Allow：
   - `evan0728@siangapato.com.tw`
   - `siang01@siangapato.com.tw`
6. 把 Access team domain 與 application AUD 填入 Worker 變數。Worker 本身還會驗證 Access JWT 的簽章、issuer、AUD 及 email 白名單；不能只靠前端或 Cookie。
7. 最後只把 Worker route 接到 `siangstock.com/api/rules*`，不攔截首頁或其他路徑。

### 目前部署狀態

- D1 與 Worker 已部署，正式同源 GET/HEAD 可讀取集中規則 v5。
- 正式 route 僅為 `siangstock.com/api/rules*`，不攔截首頁、庫存靜態頁或其他路徑。
- Cloudflare Zero Trust Free 已啟用，方案顯示每月 0 美元、最多 50 位使用者；若超過免費額度，Cloudflare 仍可能向帳戶既有付款方式收費，請由帳戶管理者留意用量。
- Access 使用 Google Workspace IdP，精確保護 `/inventory/rules-admin/*` 與 `/api/rules/admin*`。政策採預設拒絕，只允許上列兩個管理者信箱。
- Worker 會再次驗證 Access JWT 的簽章、issuer、AUD 與 email 白名單；若 Access 設定遺失或驗證失敗，管理 PUT 會拒絕，不會退回公開寫入。

D1 的 `rules_current` 只保留一份現行規則；每次更新會由資料庫 trigger 原子寫入 `rules_history`。更新 API 需帶 `expectedVersion`，若版本已改會回覆 409，避免後存的人覆蓋先存的人。

### 回復方式

- 程式：把 GitHub 功能分支回復到部署前提交，Zeabur 會回到舊靜態頁。
- API：移除 `siangstock.com/api/rules*` Worker route 即可停止攔截；不需修改現有 A 記錄。
- 規則：從 `rules_history` 取出要回復的 payload，再以目前版本透過管理 API 發布，保留完整歷史。

## 部署到 Zeabur

1. 在 Zeabur 新增 GitHub Service，選擇這個儲存庫。
